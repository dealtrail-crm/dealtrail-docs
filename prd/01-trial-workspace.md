## 1. 목적

처음 온 방문자가 개인정보를 내지 않고 **예시 데이터가 들어 있는 전용 CRM**을 바로 받는다. 방문자는 미리 만들어 둔 테스트 계정 하나를 비밀번호를 정해 24시간 빌리고, 업종을 고르면 예시 데이터가 적재된 **작업 공간**이 생긴다. 24시간이 지나면 비밀번호와 데이터가 지워지고 계정은 다음 방문자에게 돌아간다.

이 문서는 핵심 원칙(들어오자마자 써 본다)을 직접 구현하며, 백엔드 관점에서는 멀티 테넌트 격리·시드 생성·만료 대여 정리·대여 동시성이 설명 포인트다. 며칠에 걸쳐 써 보려는 방문자를 위한 회원 계정은 `07-member.md`(Epic 7)에서 다루며, 회원도 이 문서의 업종 선택·작업 공간·초기화·격리·상한 규칙을 그대로 쓴다.

## 2. 유저 스토리

- US-WS-1. 방문자로서, 이메일이나 이름을 내지 않고 체험을 시작하고 싶다. 포트폴리오를 보는 데 시간을 들이지 않기 위해.
- US-WS-2. 방문자로서, 내 관심 업종을 골라 그 업종에 맞는 예시 데이터를 보고 싶다. 빈 화면이 아니라 "쓰는 중인 CRM"을 보기 위해.
- US-WS-3. 방문자로서, 내가 만든 데이터가 다른 방문자에게 보이지 않았으면 한다. 마음 놓고 아무 값이나 입력해 보기 위해.
- US-WS-4. 방문자로서, 이 계정이 언제까지 내 것인지 알고 싶다. 브라우저를 닫았다가 돌아와도 되는지 판단하기 위해.
- US-WS-5. 방문자로서, 데이터를 망쳤을 때 전부 지우고 다시 시작하고 싶다. 처음 상태로 돌아가기 위해.
- US-WS-6. 방문자로서, 테스트 계정이 모두 사용 중이면 언제 다시 오면 되는지 알고 싶다. 헛걸음하지 않기 위해.
- US-WS-7. 운영자(사용자 본인)로서, 만료된 대여가 자동으로 반납·정리되고, "모두 사용 중"이 얼마나 자주 생기는지 알고 싶다. 비용을 통제하고 계정 수를 조정하기 위해.

## 3. 인수조건

용어는 `00-overview.md` 4장을 따른다. 특히 **계정**(로그인 주체: 테스트 계정·회원 계정)과 **Account**(CRM의 거래 대상 회사)는 다른 것이다. 세션·비밀번호·로그아웃 규칙은 `AC-COMMON-09`~`14`를 따르고 여기서는 테스트 계정에만 해당하는 것을 적는다.

### 3.1 테스트 계정 대여

- [ ] `AC-WS-01` [BE] 테스트 계정은 미리 만들어진 고정 개수(기본 5개)가 있고, 개수는 코드 변경 없이 바꿀 수 있는 설정값이다. 각 테스트 계정은 "빈 상태" 또는 "대여 중" 둘 중 하나다.
- [ ] `AC-WS-02` [FE] 첫 화면에 "체험하기" 진입점이 있고, 누르면 테스트 계정 진입 화면으로 간다. 이메일·이름 등 개인정보 입력은 없다. 빈 계정 하나로 진입하는 방식(목록에서 고르기 또는 자동 배정)은 designer가 정한다.
- [ ] `AC-WS-03` [BE] 빈 테스트 계정으로 진입할 때 방문자는 **비밀번호를 정한다** (규칙은 `AC-COMMON-10`). 그 요청이 성공한 순간 계정은 "대여 중"이 되고, 대여 시작 시각 + 대여 시간(`AC-WS-29`, 기본 24시간)이 만료 시각으로 기록된다. 만료까지 그 계정은 그 비밀번호로만 로그인된다.
- [ ] `AC-WS-04` [BE] 대여 중인 테스트 계정에 다른 비밀번호로 로그인하면 거부된다. 빈 계정에는 "비밀번호 설정 없는 로그인"이 없다 (빈 계정 진입 = 대여 시작).
- [ ] `AC-WS-05` [BE] 두 방문자가 같은 빈 계정을 동시에 빌리려 하면 **정확히 한 명만 성공**하고 나머지는 "이미 대여 중"으로 거부된다. 검증 방법: 같은 빈 계정에 대여 요청을 동시에 여러 건 보냈을 때 성공 응답이 1건이고, 계정의 비밀번호·만료 시각이 성공한 요청의 값이다. (동시성 처리 방식은 사용자 결정, ADR 후보. 자동 테스트로 남긴다)
- [ ] `AC-WS-06` [BE] 같은 IP에서 동시에 대여 중인 테스트 계정은 1개다. 이미 그 IP의 대여가 살아 있으면 새 대여는 "이미 이 네트워크에서 체험 중"으로 거부된다. (프록시·로드밸런서 뒤에서 방문자 IP를 식별하는 방법은 infra·사용자가 정한다)
- [ ] `AC-WS-07` [공통] 모든 테스트 계정이 대여 중이면 FE는 체험 계정이 모두 사용 중임과 가장 빨리 비는 시각을 알린다. BE는 가장 이른 만료 시각을 돌려준다. 이 화면에서 회원가입(`07-member.md` `AC-MB-08`)으로 갈 수 있다.
- [ ] `AC-WS-08` [BE] "모두 사용 중" 상황이 발생할 때마다(대여 시도가 그 이유로 실패할 때마다) 발생 시각과 가장 이른 만료 시각이 로그로 남는다. 테스트 계정 수를 늘릴지 판단하는 근거다.
- [ ] `AC-WS-09` [공통] 테스트 계정의 비밀번호 찾기·변경은 없다. 잊으면 만료 시각에 자동 반납된다. FE는 비밀번호를 정하는 화면에서 이 사실을 안내한다.

### 3.2 세션과 만료 안내 (테스트 계정)

- [ ] `AC-WS-10` [공통] 테스트 계정의 세션(`AC-COMMON-12`)은 대여 만료 시각까지 유지된다. 로그아웃(`AC-COMMON-14`)해도 대여와 데이터는 유지되며, 만료 전이면 같은 비밀번호로 다시 로그인할 수 있다.
- [ ] `AC-WS-11` [FE] 대여가 만료된 세션으로 접근하면 체험이 끝났음을 알리고 새로 시작하는 버튼을 보여 준다. (세션이 없거나 유효하지 않은 경우의 안내는 `AC-COMMON-09`)

### 3.3 업종 선택과 작업 공간 생성

이 절과 3.4·3.5는 테스트 계정과 회원 계정에 똑같이 적용된다 (`07-member.md` `AC-MB-05`).

- [ ] `AC-WS-12` [FE] 작업 공간이 없는 계정으로 로그인하면(테스트 계정 대여 직후, 회원 가입 직후, 초기화 직후) 업종 선택 화면으로 간다. 화면은 `00-overview.md` 4.1의 업종 15개를 각각 한 줄 설명과 함께 **모두** 보여 준다. 예시 데이터가 있는 3개(제조, IT·소프트웨어, 전문 서비스)만 선택할 수 있고, 나머지 12개는 "준비 중"으로 비활성 표시한다. 선택 가능한 업종 하나를 고르면 즉시 작업 공간이 생성되고 파이프라인 화면으로 이동한다.
- [ ] `AC-WS-13` [BE] 업종을 받아 로그인한 계정에 속한 새 작업 공간을 만들고, 그 업종의 예시 데이터를 **생성 요청 한 번에** 적재한다. 적재가 끝난 작업 공간만 방문자에게 돌려준다. (반쯤 적재된 공간이 보이지 않는다)
- [ ] `AC-WS-14` [BE] 예시 데이터 적재 중 일부가 실패하면 작업 공간 자체가 남지 않는다. (빈 공간이나 일부만 채워진 공간이 생기지 않는다)
- [ ] `AC-WS-15` [공통] 업종 선택부터 파이프라인 화면에 예시 데이터가 보이기까지 체감 대기 시간이 수 초 이내다. 그 사이 FE는 로딩 상태를 보여 준다.
- [ ] `AC-WS-16` [BE] 목록에 없는 업종, 또는 목록에는 있지만 예시 데이터가 없는("준비 중") 업종으로 생성을 요청하면 거부된다. 거부 사유는 두 경우가 구분된다.
- [ ] `AC-WS-17` [BE] 한 계정(테스트 계정의 현재 대여, 또는 회원 계정)에는 작업 공간이 **최대 하나**만 있다. 이미 작업 공간이 있는 계정에 업종 선택으로 새 공간을 만들려 하면 거부된다 (새로 시작하려면 3.5 초기화). 모든 CRM 요청은 로그인한 계정의 작업 공간을 대상으로 하며, 요청에 다른 작업 공간을 지정할 수 없다.

### 3.4 예시 데이터

- [ ] `AC-WS-18` [BE] 업종별 예시 데이터는 아래 다섯 종류를 모두 포함한다: Lead(미전환 상태 포함), Account(업종 값 포함, `03-account-contact.md` `AC-ACC-11`), Contact, Opportunity(모든 단계에 1건 이상, 수주·실패 포함), Activity. 규모와 구성은 3.4.1을 따른다.
- [ ] `AC-WS-19` [BE] 같은 업종으로 만든 두 작업 공간은 **내용은 같되 서로 다른 식별자**를 가진 별개의 데이터를 가진다. 한쪽을 수정해도 다른 쪽에 영향이 없다.
- [ ] `AC-WS-20` [BE] 예시 데이터의 날짜(예상 마감일, 활동 시각 등)는 작업 공간 생성 시각을 기준으로 상대적으로 잡혀, 언제 체험해도 "최근" 데이터로 보인다. (예: 작성 시점에 고정된 2026-03-01 같은 날짜가 아니라 "생성일 + 14일")
- [ ] `AC-WS-21` [공통] 예시 데이터에 쓰인 회사명·인명은 모두 가상이며 실존 기업·인물과 겹치지 않도록 작성한다. 실존 상용 CRM 제품의 데모 데이터를 복제하지 않는다.
- [ ] `AC-WS-22` [BE] "준비 중" 업종에 예시 데이터를 붙일 때 애플리케이션 코드 구조를 바꾸지 않고 예시 데이터 정의만 추가하면 되도록 한다. (구현 방식은 사용자 결정. PRD는 "업종 추가가 데이터 추가 수준의 작업"임을 요구한다)

세 업종은 금액대·주기가 서로 달라 업종을 바꾸면 칸반과 대시보드가 다르게 보여야 한다. Account 업종은 작업 공간 업종과 무관하게 고객사의 실제 산업을 따르며, 한 작업 공간 안에서 2종 이상이 섞이도록 한다.

전체 회사명·인명·거래명·금액·날짜 오프셋은 업종별 명세에 쓴다: 공통 규칙 [`seed/README.md`](./seed/README.md), [`seed/manufacturing.md`](./seed/manufacturing.md), [`seed/it-software.md`](./seed/it-software.md), [`seed/professional-services.md`](./seed/professional-services.md). 명세의 기계 판독 형식(JSON·YAML·SQL 등)은 사용자가 정한다.

### 3.5 초기화

- [ ] `AC-WS-23` [FE] 대시보드에 **초기화** 버튼이 있다. 누르면 작업 공간의 모든 데이터가 즉시 삭제됨을 알리는 확인을 거친 뒤 실행되고, 완료되면 업종 선택 화면으로 돌아간다. 테스트 계정이면 남은 시간이 그대로 보인다.
- [ ] `AC-WS-24` [BE] 초기화는 로그인한 계정의 작업 공간과 그 안의 모든 데이터(Lead, Account, Contact, Opportunity, 단계 이력, Activity)를 즉시 삭제한다. 계정(테스트 계정이면 대여의 비밀번호·만료 시각)과 로그인 상태는 그대로다. 이후 업종 선택으로 새 작업 공간을 만들 수 있고, 이전과 다른 업종을 골라도 된다.
- [ ] `AC-WS-25` [BE] 초기화는 전부 지워지거나 전혀 지워지지 않는다. 도중에 실패하면 이전 작업 공간이 그대로 남고, 반쯤 지워진 상태가 방문자에게 보이지 않는다.

### 3.6 격리와 접근

- [ ] `AC-WS-26` [BE] `AC-COMMON-01`, `AC-COMMON-02`가 모든 엔티티에 대해 성립한다. 검증 방법: 계정 두 개(테스트 계정 두 개, 또는 테스트 계정과 회원 계정)로 각각 작업 공간을 만들고, 한쪽 세션으로 다른 쪽의 Lead·Account·Contact·Opportunity·Activity를 조회·수정·삭제·단계 변경 시도했을 때 전부 "존재하지 않음"으로 처리된다. 또한 한쪽 세션으로 자기 Lead를 전환하면서 다른 쪽의 Account 식별자를 기존 Account로 지정하는 시도(`02-lead.md` `AC-LD-19`)는 "존재하지 않음"으로 거부되고, 아무 엔티티도 만들어지지 않으며 Lead 상태가 그대로다.
- [ ] `AC-WS-27` [BE] 작업 공간 식별자와 계정 식별자는 추측 불가능하다 (순차 번호 금지).
- [ ] `AC-WS-28` [BE] 반납된 테스트 계정을 새로 빌린 방문자는 이전 대여의 작업 공간과 데이터를 어떤 경로로도 볼 수 없다. 이전 대여의 데이터가 아직 정리 작업으로 삭제되기 전이어도 같다. 검증 방법: 대여 A를 만료시킨 뒤 정리 작업을 실행하지 않은 채 같은 계정을 대여 B로 빌려 로그인했을 때, 작업 공간이 없는 상태(업종 선택 화면)로 시작하고 A의 데이터가 어떤 조회에도 나오지 않는다.

### 3.7 만료와 정리

- [ ] `AC-WS-29` [BE] 테스트 계정 대여는 대여 시작 시각 + **대여 시간**을 만료 시각으로 가진다. 대여 시간은 코드 변경 없이 바꿀 수 있는 설정값이고 기본값은 **24시간**이다. 만료 시각은 대여 시작 시점에 기록되며(`AC-WS-03`) FE가 조회할 수 있다.
- [ ] `AC-WS-30` [FE] `AC-COMMON-08`: 테스트 계정으로 로그인한 동안 남은 시간 또는 만료 시각이 모든 화면에서 보인다. 남은 시간이 1시간 이하이면 그 표시가 경고 표시로 바뀐다. 팝업·모달은 띄우지 않는다 (표시 방식은 designer가 정한다).
- [ ] `AC-WS-31` [BE] 만료 시각이 지나면 정리 작업이 돌기 전이라도 그 대여의 세션으로 오는 모든 요청이 "만료됨"으로 거부된다. 같은 시점부터 그 테스트 계정은 새 대여가 가능하다 (`AC-WS-07`의 "가장 빨리 비는 시각"은 곧 가장 이른 만료 시각이다).
- [ ] `AC-WS-32` [BE] 만료된 대여의 비밀번호, 작업 공간, 그에 속한 모든 데이터(Lead, Account, Contact, Opportunity, 단계 이력, Activity)를 주기적으로 삭제하는 정리 작업이 있다. 실행 주기는 코드 변경 없이 바꿀 수 있는 설정값이며, 기본값에서 만료 후 삭제 완료까지 허용 지연은 **1시간 이내**다. 검증 방법: 대여 시간(`AC-WS-29`)과 정리 주기를 분 단위로 짧게 설정한 환경에서 대여 → 만료 → 비밀번호·작업 공간·데이터 삭제와 계정 반납이 설정값대로 일어나는 것을 코드 변경 없이 확인할 수 있다. (시연 환경에서 정리 배치를 실시간으로 보여 주기 위한 것)
- [ ] `AC-WS-33` [BE] 정리 작업은 **만료되지 않은** 대여와 회원 계정의 데이터를 절대 건드리지 않는다. 검증 방법: 만료 대여, 미만료 대여, 회원 작업 공간이 섞인 상태에서 정리 작업을 실행하면 만료 대여의 것만 사라지고 나머지의 모든 엔티티 수가 그대로다.
- [ ] `AC-WS-34` [BE] 정리 작업이 도중에 실패해도 다음 실행에서 남은 만료 대여를 이어서 정리한다. 한 대여의 삭제가 실패해도 다른 대여의 정리를 막지 않는다.
- [ ] `AC-WS-35` [BE] 정리 작업의 실행 결과(실행 시각, 반납한 계정 수, 삭제한 작업 공간 수)가 로그로 남아 "실제로 정리되고 있음"을 확인할 수 있다. (`00-overview.md` 성공 지표 3)
- [ ] `AC-WS-36` [BE] 정리 작업이 두 번 동시에 실행되거나, 같은 계정에 대한 새 대여(`AC-WS-31`)·사용 중인 공간의 요청과 겹쳐도 데이터가 깨지지 않는다. (동시성 처리 방식은 사용자 결정, ADR 후보)

### 3.8 남용 방지 (최소)

- [ ] `AC-WS-37` [BE] 작업 공간당 엔티티별 생성 상한은 **200건**(Lead·Account·Contact·Opportunity·Activity 각각)이며, 넘으면 생성이 거부된다. 단계 이력은 Opportunity에 종속되므로 별도 상한이 없다. Lead 전환처럼 한 요청이 여러 엔티티를 만들 때는 어느 하나라도 상한을 넘으면 요청 전체가 거부된다. 거부 사유가 FE에 전달된다.
- [ ] `AC-WS-38` [FE] 상한에 걸리면 작업 공간의 생성 한도에 도달했음을 안내한다.

## 4. 제외 범위

- 테스트 계정 대여 연장, 만료 전 알림
- 계정 하나에 작업 공간 여러 개, 작업 공간 안의 다중 사용자·권한
- 업종별 예시 데이터를 부분적으로 되돌리기 (초기화는 전체 삭제만)
- 업종 선택 뒤 "빈 공간으로 시작" 옵션
- IP 동시 대여 1개 외의 방문자 단위 제한 (생성 횟수 제한 등)
- 관리자 화면 (테스트 계정 상태 조회·강제 반납은 로그와 DB로 대신한다)
- 회원가입·회원 로그인 (`07-member.md`)

## 5. 의존성 / 열린 질문

- 예시 데이터의 실제 값은 `prd/seed/`의 업종별 명세를 따른다. 명세는 "무엇이 들어 있어야 하는가"만 정의하며, 생성 시각·이력 시각은 명세의 상대 날짜대로 과거 시각으로 적재한다. 기계 판독 형식과 적재 방식은 사용자(백엔드)가 구현 단계에서 정한다(`seed/README.md` "구현 시 결정").
- 정리 작업의 실행 방식은 앱 안 스케줄러다(HANDOFF 1장). 대여 시간과 정리 주기의 설정 방식(프로퍼티·환경 변수 등)과 시연 환경에서 쓸 값은 사용자가 구현 단계에서 정한다. PRD는 두 값을 코드 변경 없이 바꿀 수 있다는 것과 기본값에서 "만료 후 1시간 안에 삭제된다"만 요구한다.
- 방문자 IP 식별 방법은 infra에서 정한다.
- 빈 테스트 계정 진입 방식(목록 선택 / 자동 배정)은 designer가 화면 흐름에서 정한다.
