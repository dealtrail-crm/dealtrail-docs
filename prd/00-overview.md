# 00. 제품 개요 (v0.1 MVP)

## 1. 한 줄 정의

**dealtrail**은 개인정보 없이 바로 써 볼 수 있는 미니 B2B 영업 CRM이다. 방문자는 테스트 계정을 24시간 빌리거나 아이디·비밀번호만으로 가입한 뒤, 업종을 고르면 예시 데이터가 들어 있는 전용 작업 공간을 받고, Lead를 Opportunity로 전환하고 파이프라인을 진행시키며 대시보드에서 결과를 본다. 테스트 계정의 데이터는 24시간 뒤 자동 삭제된다.

이름의 의미(deal + trail): 영업 건이 단계를 거치며 남긴 **이력**. 단계 변경 이력은 이 제품의 정체성이다.

## 2. 목표와 비목표

### 목표

| # | 목표 | 확인 방법 |
|---|---|---|
| G1 | 방문자가 첫 화면에서 **클릭 몇 번 안에** 데이터가 들어 있는 CRM을 직접 조작한다 | 체험 시작 → 파이프라인 화면까지 개인정보 입력 없이, 테스트 계정 비밀번호 설정과 업종 선택만으로 도달 |
| G2 | 백엔드 설명 포인트 4가지가 **동작으로** 드러난다 | Lead 전환 원자성, 단계 상태 머신·이력, 작업 공간 격리·시드·만료 대여 정리, 파이프라인 집계 |
| G3 | 작업 공간끼리 데이터가 섞이지 않고, 만료된 테스트 계정 대여의 데이터는 사라진다 | 계정 A의 세션으로 계정 B의 데이터에 어떤 경로로도 접근 불가 |
| G4 | 포트폴리오 평가자가 이슈·PR·ADR·트러블슈팅을 따라가며 의사결정 과정을 읽을 수 있다 | 각 Epic·작업 이슈가 이 PRD의 인수조건 ID를 인용 |

### 비목표 (MVP에서 하지 않는 것, HANDOFF 0장 표 그대로)

- 노코드 화면·필드 커스터마이징
- 자동화 엔진 (Flow 류)
- 이메일·캘린더 연동
- 견적·계약서 생성
- 다중 조직·복잡한 권한 계층 (계정 하나 = 작업 공간 하나 = 사용자 한 명)
- 소셜 로그인, 이메일 인증, 비밀번호 찾기 (개인정보를 받지 않으므로 복구 수단도 없다)
- Salesforce 등 특정 제품의 이름·로고·화면 모방

## 3. 대상 사용자

| 역할 | 설명 | 이 제품에서 하는 일 |
|---|---|---|
| **방문자 (테스트 계정)** | 포트폴리오를 보러 온 사람 (채용 담당자, 개발자, 리뷰어) | "체험하기" → 테스트 계정 비밀번호 설정 → 업종 선택 → 24시간 동안 작업 공간에서 자유롭게 조작 |
| **방문자 (회원)** | 며칠에 걸쳐 써 보려는 사람 | 아이디·비밀번호로 가입 → 업종 선택 → 만료 없는 작업 공간에서 조작 (`07-member.md`) |
| **영업 담당자 (체험 속 역할)** | 방문자가 작업 공간 안에서 맡는 가상 역할 | Lead 등록·검증·전환, Opportunity 단계 이동, 활동 기록, 대시보드 확인 |
| **운영자** | 사용자 본인 | 테스트 계정 수 조정, 정리 로그 확인 |

작업 공간 안에는 사용자 한 명뿐이며 역할 구분이 없다.

## 4. 핵심 개념 (용어)

HANDOFF 0장의 정의를 그대로 쓰고, PRD에서 쓰는 보조 용어를 추가한다.

| 용어 | 정의 |
|---|---|
| **계정** | 로그인 주체. 테스트 계정 또는 회원 계정. CRM의 **Account(거래 대상 회사)와는 다른 것**이며, 문서에서 로그인 주체는 항상 한국어 "계정"으로, 거래처는 영문 "Account"로 쓴다 |
| **테스트 계정 (Trial Account)** | 미리 만들어 둔 고정 개수(기본 5개, 설정값)의 공용 계정. 빈 상태 또는 대여 중 상태를 가진다 |
| **대여 (Rental)** | 방문자가 빈 테스트 계정에 비밀번호를 정해 24시간 동안 독점하는 것. 대여 시작 시각과 만료 시각을 가진다. 만료되면 비밀번호와 데이터가 지워지고 계정은 빈 상태로 돌아간다(반납) |
| **회원 계정 (Member)** | 아이디·비밀번호만으로 가입한 계정. 만료 시각이 없고 기간 없이 영구 보관한다 |
| **세션** | 로그인 상태. 브라우저를 닫아도 유지된다 |
| **작업 공간 (Workspace)** | CRM 데이터의 격리 단위. 테스트 계정의 대여 하나 또는 회원 계정 하나에 속하며, 계정당 최대 하나다. 모든 CRM 데이터는 정확히 하나의 작업 공간에 속한다. 업종을 가진다 |
| **업종 (Industry)** | 회사의 산업 분류. 두 곳에 쓴다. (1) 작업 공간의 업종: 체험 시작 시 선택하며, 방문자가 맡는 영업 조직의 업종이자 예시 데이터 세트의 종류. (2) Account의 업종: 고객사의 산업 분류. 값은 모두 4.1의 고정 목록에서 고른다 |
| **예시 데이터 (Seed)** | 작업 공간 생성 시 업종에 맞춰 미리 넣어 두는 Lead·Account·Contact·Opportunity·Activity |
| **Lead** | 아직 검증되지 않은 잠재 고객. 회사명·담당자명·연락처 정도의 정보 |
| **검증 (Qualify)** | Lead가 영업 가치가 있다고 표시하는 행위. Lead 상태는 신규·진행 중·검증됨·전환됨·제외 (`02-lead.md` §3.2) |
| **전환 (Convert)** | 검증된 Lead로부터 Account + Contact + Opportunity를 한 번에 만드는 행위. Account는 새로 만들거나 같은 작업 공간의 기존 Account를 선택할 수 있고, Contact·Opportunity는 항상 새로 만든다. 전환 후 Lead는 더 이상 수정하지 않는다 |
| **Account** | 거래 대상 회사 |
| **Contact** | Account에 속한 담당자 |
| **Opportunity** | 진행 중인 영업 건. 금액, 단계, 예상 마감일을 가진다 |
| **단계 (Stage)** | Opportunity의 진행 상태. 열린 단계 발굴 → 제안 → 협상과 종료 단계 수주·실패로 나뉜다. 허용 전이는 `04-opportunity-pipeline.md` §3.2 |
| **단계 이력 (Stage History)** | Opportunity의 단계가 바뀔 때마다 남는 기록 (이전 단계, 새 단계, 시각) |
| **Activity** | 통화·미팅·할 일 기록. 어떤 대상에 붙는지는 TBD-8 |
| **파이프라인** | 열린 Opportunity를 단계별로 나열한 칸반 뷰 |
| **수주율 (Win Rate)** | 종료된 Opportunity 중 수주 비율. 계산 기준은 TBD-4 |

### 4.1 업종 목록 (고정)

B2B 영업 CRM에서 고객사 업종으로 흔히 쓰는 분류를 한국표준산업분류(KSIC)·ISIC 대분류 기준으로 묶은 15개. 작업 공간 업종 선택 화면과 Account 업종 필드가 같은 목록을 쓴다. 업종 이름은 짧은 표기를 그대로 화면·API에 쓴다.

| # | 업종 | 선택 화면 한 줄 설명 | 예시 데이터 |
|---|---|---|---|
| 1 | 제조 | 공장·설비에 부품과 자재를 납품하는 영업 | 있음 |
| 2 | IT·소프트웨어 | 기업용 소프트웨어 구독과 시스템 구축 영업 | 있음 |
| 3 | 전문 서비스 | 기업 고객에게 컨설팅·캠페인·자문 프로젝트를 수주하는 영업 | 있음 |
| 4 | 통신 | 기업 전용 회선·통신 서비스 영업 | 준비 중 |
| 5 | 금융·보험 | 기업 대상 금융 상품·단체보험 영업 | 준비 중 |
| 6 | 의료·헬스케어 | 병원·의원에 의료기기와 소모품을 공급하는 영업 | 준비 중 |
| 7 | 유통·도매 | 소매점·프랜차이즈에 상품을 공급하는 도매 영업 | 준비 중 |
| 8 | 물류·운송 | 화주 기업에 운송·창고 서비스를 제안하는 영업 | 준비 중 |
| 9 | 건설·부동산 | 건축·인테리어 공사와 상업용 부동산 임대 영업 | 준비 중 |
| 10 | 인력·사업 지원 | 기업에 인력 파견·채용 대행·시설 관리를 제공하는 영업 | 준비 중 |
| 11 | 교육 | 기업 임직원 교육 프로그램을 판매하는 영업 | 준비 중 |
| 12 | 미디어·엔터테인먼트 | 광고 지면·콘텐츠·행사 스폰서십을 기업에 판매하는 영업 | 준비 중 |
| 13 | 숙박·외식·여행 | 기업 행사·워크숍·출장 숙박을 유치하는 영업 | 준비 중 |
| 14 | 에너지·유틸리티 | 공장·건물에 전력 설비·에너지 절감 솔루션을 공급하는 영업 | 준비 중 |
| 15 | 공공·비영리 | 공공기관·비영리 단체 (고객사 업종으로만 쓰임) | 준비 중 |

- "있음"인 업종만 작업 공간 생성 시 선택할 수 있다 (`01-trial-workspace.md` `AC-WS-12`). "준비 중"은 화면에 보이되 선택할 수 없다.
- Account 업종 필드는 15개 모두 값으로 쓸 수 있다 (`03-account-contact.md` `AC-ACC-01`).
- 업종 추가·이름 변경은 이 표를 고치는 것으로 확정한다.

## 5. 핵심 흐름

```
[첫 화면] ─┬─ "체험하기" ──> [빈 테스트 계정에 비밀번호 설정 = 대여 시작, 24시간] ─┐
           │                  (모두 사용 중이면 "가장 빨리 비는 시각" 안내)         │
           └─ "회원가입 / 로그인" ──> [아이디·비밀번호] ──────────────────────────┘
                                                    │
                                                    v
                              [업종 선택] ──> [작업 공간 생성 + 예시 데이터 적재]
                                                    │
                                                    v
            ┌──────────────── [파이프라인 칸반] (기본 진입 화면) ────────────────┐
            │                                                                   │
   [Lead 목록] ── 검증 ── 전환 ──> Account + Contact + Opportunity (한 번에 생성)   │
            │                                                                   │
   [Opportunity 상세] ── 단계 이동 (허용된 전이만) ── 이력 누적 ── 활동 기록         │
            │                                                                   │
   [대시보드] ── 단계별 금액 합계, 수주율 ── [초기화] ──> 데이터 삭제 → 업종 선택     │
            │                                                                   │
            └── (테스트 계정) 만료 ──> 접근 차단, 계정 반납 ──> 정리 배치가 데이터 삭제 ┘
```

- 로그인 후 처음 보는 화면은 **업종 선택**, 그다음이 **파이프라인 칸반**이다. 예시 데이터가 이미 단계별로 흩어져 있어 "쓰는 중인 CRM"처럼 보여야 한다 (G1).
- 테스트 계정 흐름에서 첫 화면부터 파이프라인까지 **필수 입력은 비밀번호 설정과 업종 선택 둘**이다. 개인정보는 없다.
- 회원도 가입 직후 같은 흐름(업종 선택 → 예시 데이터 → 초기화 가능)을 탄다. 차이는 만료 시각과 남은 시간 표시가 없다는 것뿐이다.

## 6. 공통 요구사항 (모든 기능에 적용)

인수조건 ID 접두어 `AC-COMMON`. 각 기능 문서는 이 항목을 반복하지 않고 참조한다.

- [ ] `AC-COMMON-01` [BE] 모든 CRM 데이터(Lead, Account, Contact, Opportunity, Activity, 단계 이력)는 정확히 하나의 작업 공간에 속하며, 작업 공간 밖에서는 존재하지 않는 것으로 취급된다. 작업 공간은 테스트 계정의 대여 하나 또는 회원 계정 하나에 속한다.
- [ ] `AC-COMMON-02` [BE] 계정 A의 세션으로 계정 B의 작업 공간 데이터를 조회·수정·삭제하려 하면 "존재하지 않음"과 같은 결과를 받는다. (데이터가 있다는 사실 자체가 드러나지 않는다)
- [ ] `AC-COMMON-03` [BE] 만료된 테스트 계정 대여의 세션으로 오는 요청은 읽기·쓰기 모두 거부된다. 거부 응답은 "만료됨"으로 구분되어 FE가 안내 화면을 띄울 수 있다.
- [ ] `AC-COMMON-04` [공통] 목록 조회(Lead·Account·Contact·Opportunity·Activity)는 **페이지네이션을 둔다**. 페이지 크기, 방식(offset·cursor 등), 정렬·필터 파라미터 형태는 API 계약에서 정하고 사용자가 승인한다. 칸반·대시보드처럼 전체 집계가 필요한 조회를 예외로 둘지도 API 계약에서 정한다. 작업 공간당 엔티티별 상한은 200건이며(`01-trial-workspace.md` `AC-WS-37`) 넘는 생성은 거부된다.
- [ ] `AC-COMMON-05` [BE] 입력 검증 실패(필수값 누락, 형식 오류, 허용되지 않은 상태 전이)는 어떤 필드가 왜 실패했는지 FE가 표시할 수 있는 형태로 돌아온다.
- [ ] `AC-COMMON-06` [공통] 금액은 KRW(원) 하나로 정수 표현한다. 통화 변환은 없다. 화면 표시 형식은 designer가 정한다.
- [ ] `AC-COMMON-07` [공통] 화면·문구·로고는 자체 제작이며 특정 상용 CRM을 모방하지 않는다. (designer 검토 항목)
- [ ] `AC-COMMON-08` [FE] 테스트 계정으로 로그인한 동안 대여의 **남은 시간(또는 만료 시각)** 이 화면 어딘가에 항상 보인다. 회원 계정에는 표시하지 않는다.
- [ ] `AC-COMMON-09` [공통] 모든 CRM 요청은 로그인 세션이 있어야 한다. 세션이 없거나 유효하지 않으면 "인증 필요"로 거부되고, FE는 첫 화면으로 안내한다.
- [ ] `AC-COMMON-10` [공통] 비밀번호는 **8자 이상**이고 구성 제한이 없다. 테스트 계정 대여 비밀번호와 회원 비밀번호에 같은 규칙을 쓴다. 규칙에 맞지 않으면 `AC-COMMON-05` 형식으로 거부되고 FE는 입력란 옆에 규칙을 보여 준다.
- [ ] `AC-COMMON-11` [BE] 비밀번호는 원문을 저장하지 않는다. (저장 방식은 사용자 결정)
- [ ] `AC-COMMON-12` [공통] 로그인 세션은 브라우저를 닫았다 열어도 유지된다. 별도 "로그인 유지" 옵션은 없다. 유지 기간은 테스트 계정은 대여 만료 시각까지(`01` `AC-WS-10`), 회원은 API 계약에서 정한 상한까지(`07` `AC-MB-03`)다.
- [ ] `AC-COMMON-13` [BE] 세션 식별자는 추측 불가능하고(순차 값 금지), 보관 수단(쿠키 등)과 형식은 API 계약에서 정한다. 작업 공간·계정 식별자를 아는 것만으로는 아무 데이터에도 접근할 수 없다. 접근은 로그인 세션으로만 된다.
- [ ] `AC-COMMON-14` [공통] 로그아웃할 수 있다. 로그아웃은 세션만 끝내고 계정과 작업 공간 데이터는 그대로 둔다.

## 7. 데이터 관계 (개념 수준)

```
계정(테스트 계정의 현재 대여 또는 회원 계정) 1 ─── 0..1 Workspace

Workspace 1 ─── * Lead
          1 ─── * Account 1 ─── * Contact
          1 ─── * Opportunity * ─── 1 Account
                              * ─── 0..1 Contact (주 담당자)
                              1 ─── * StageHistory
          1 ─── * Activity ─── 대상(TBD-8)
Lead(전환됨) ─── 1 Account(새로 만든 것 또는 선택한 기존 것), 1 Contact, 1 Opportunity (전환으로 연결·생성된 것)
```

저장 구조·키 설계는 PRD 범위가 아니다 (사용자 결정, 필요 시 ADR).

## 8. 성공 지표 (포트폴리오 관점)

정량 지표는 없다. 아래가 모두 "예"면 MVP 완료로 본다.

1. 처음 온 사람이 안내 없이 체험을 시작해 Lead 하나를 전환하고 Opportunity를 수주까지 옮길 수 있는가
2. 백엔드 설명 포인트 4가지 각각에 대응하는 인수조건이 통과했고, 관련 ADR 또는 트러블슈팅이 1건 이상 있는가
3. 만료된 테스트 계정 대여가 실제로 반납·정리되는 것을 로그나 데이터로 확인할 수 있는가
