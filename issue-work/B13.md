## 배경

만료된 대여의 비밀번호·작업 공간·데이터를 주기적으로 지우고 계정을 반납하는 배치다. 실행 방식은 **앱 안 스케줄러(Spring `@Scheduled`)로 확정**됐고 외부 트리거는 두지 않는다 (HANDOFF 1장). 실행 주기는 코드 변경 없는 설정값이며 기본값에서 허용 지연 1시간을 지킨다. 시연 환경에서는 대여 시간({{B03}})과 함께 분 단위로 짧게 두어 배치를 실시간으로 보여 준다. 이 Epic의 설명 포인트 "만료 대여 정리 배치"의 **핵심 이슈**다. 만료 판정 자체는 {{B06}}에서 시각 비교로 먼저 성립한다.

- Epic: {{E1}}
- 선행: {{B03}}, {{B06}}, {{B10}}
- 설명 포인트: **만료 대여 정리 배치 (핵심)**

## 유저 스토리

- `US-WS-7` 운영자로서, 만료된 대여가 자동으로 반납·정리되길 원한다. 비용을 통제하고 계정 수를 조정하기 위해.

## 인수조건

- [ ] `AC-WS-32` 만료된 대여의 비밀번호, 작업 공간, 그에 속한 모든 데이터(Lead, Account, Contact, Opportunity, 단계 이력, Activity)를 주기적으로 지우고 계정을 빈 상태로 돌린다. 실행 주기는 코드 변경 없는 설정값이며, 기본값에서 만료 후 정리까지 허용 지연은 1시간 이내. 검증: 대여 시간(`AC-WS-29`)과 정리 주기를 분 단위로 짧게 설정한 환경에서 대여 → 만료 → 비밀번호·작업 공간·데이터 삭제와 계정 반납이 설정값대로 일어남을 코드 변경 없이 확인
- [ ] `AC-WS-33` 정리 작업은 만료되지 않은 대여와 회원 계정의 데이터를 절대 건드리지 않는다. 검증: 만료 대여·미만료 대여·회원 작업 공간을 함께 둔 뒤 실행 → 만료 것만 사라짐 (`AC-MB-04` 회원은 대상 아님)
- [ ] `AC-WS-34` 도중 실패해도 다음 실행에서 남은 만료 대여를 이어서 정리한다. 한 대여의 삭제 실패가 다른 대여의 정리를 막지 않는다 (실패 주입 테스트)
- [ ] `AC-WS-35` 실행 결과(실행 시각, 반납한 계정 수, 삭제한 작업 공간 수)가 로그로 남는다
- [ ] `AC-WS-36` 정리 작업이 두 번 동시에 실행되거나, 같은 계정의 새 대여(`AC-WS-31`)·사용 중 공간의 요청과 겹쳐도 데이터가 깨지지 않는다 (새 대여의 데이터를 지우지 않음, 이중 삭제 오류 없음). 동시 실행 자동 테스트

## 구현 시 결정할 것 (ADR 소재)

- 대여 모델링: 테스트 계정 행에 대여 컬럼(비밀번호·시작·만료)을 두는가, 대여를 별도 행으로 분리하는가. 분리하면 `AC-WS-28`과 정리 대상 식별이 쉬워지는 대신 조인이 늘어난다 ({{B03}}과 공유하는 결정)
- 중복 실행 방지의 위치(`AC-WS-36`): 스케줄러 수준 락(ShedLock 등)으로 한 번에 하나만 돌게 하는가, 행 단위 원자 처리(`FOR UPDATE SKIP LOCKED` 등)로 둘이 돌아도 한 대여를 한 번만 집게 하는가. 현재 배포는 EC2 한 대·인스턴스 하나(HANDOFF 1장)지만 둘 이상이 될 때 답이 달라지는지 명시한다
- 테스트용 보호된 수동 트리거를 둘 것인가 (`AC-WS-33` `34` 검증·운영 확인용). 둔다면 인증 방식과 노출 범위
- 정리 주기 설정값의 방식(프로퍼티·환경 변수 등)과 기본값. 기본값은 `AC-WS-32`의 허용 지연 1시간 안이어야 하고, 시연 환경에서는 대여 시간({{B03}})과 함께 분 단위로 줄일 수 있어야 한다. 설정값으로 두는 것 자체는 결정됨 (`prd/99-decisions-tbd.md` TBD-26)
- ADR 범위: **실행 방식 + 동시 실행 방지를 하나의 ADR로 묶는 것을 권장**. 대여 모델링은 같은 ADR에 포함할지 분리할지 그때 정한다

## 비고

**AC 5개 예외**: 실행 방식과 동시 실행 방지를 하나의 ADR로 묶기로 했으므로 이슈도 하나로 둔다.
