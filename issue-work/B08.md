## 배경

`prd/seed/` 명세를 기계 판독 가능한 형식으로 옮기고, 작업 공간 생성 시각 기준의 상대 날짜로 적재하며, 일부 실패 시 공간이 남지 않게 한다. 새 업종은 코드 변경 없이 데이터 정의만 추가하면 되는 구조여야 한다. 이 Epic의 설명 포인트 "작업 공간 생성·시드"의 **핵심 이슈**다.

- Epic: {{E1}}
- 선행: {{B07}}
- 설명 포인트: **작업 공간 생성·시드 (핵심)**

## 유저 스토리

- `US-WS-2` 방문자로서, 빈 화면이 아니라 "쓰는 중인 CRM"을 보고 싶다.
- `US-WS-3` 방문자로서, 내 데이터가 다른 방문자 것과 섞이지 않길 원한다.

## 인수조건

- [ ] `AC-WS-14` 적재 중 일부가 실패하면 작업 공간 자체가 남지 않는다 (빈 공간·일부만 채워진 공간 없음). 실패 주입 테스트로 확인한다
- [ ] `AC-WS-19` 같은 업종으로 만든 두 작업 공간은 내용은 같되 서로 다른 식별자를 가진 별개 데이터다. 한쪽 수정이 다른 쪽에 영향 없다
- [ ] `AC-WS-20` 예시 데이터의 날짜·시각(`D±n`, `prd/seed/README.md` 표기 규칙)은 생성 시각 기준 상대값으로 적재되어 언제 체험해도 "지연 2건·오늘 기한 1건" 등 명세의 모양이 유지된다 (한국 시간 `AC-COMMON-15`)
- [ ] `AC-WS-22` "준비 중" 업종에 예시 데이터를 붙일 때 애플리케이션 코드 구조를 바꾸지 않고 데이터 정의만 추가하면 된다. PR 설명에 "새 업종 추가 절차"를 적는다

## 구현 시 결정할 것 (ADR 소재)

- 명세의 기계 판독 형식: JSON / YAML / SQL / 코드(Java) 중 무엇으로, 어디에 두는가. `prd/seed/*.md`와 어긋나지 않게 유지하는 방법
- 과거 시각(이력 시각, 활동 시각) 적재 방법 — 생성 시각 기준 오프셋 계산 위치
- 업종 추가가 "데이터 추가" 수준이 되는 구조 (업종 → 데이터 정의 매핑, 준비 중 판정)
- 적재 실패 시 공간이 남지 않게 하는 트랜잭션 경계 (생성·적재를 한 트랜잭션으로 묶는가, 보상 삭제를 하는가)
