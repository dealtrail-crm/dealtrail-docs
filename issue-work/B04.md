## 배경

두 방문자가 같은 빈 계정을 동시에 빌리려 하면 정확히 한 명만 성공해야 하고, 같은 IP는 동시에 1개만 빌릴 수 있다. 둘 다 "동시 요청 중 하나만 통과" 규칙이며 이 Epic의 백엔드 설명 포인트 "테스트 계정 동시 대여 경쟁"의 **핵심 이슈**다. ADR·트러블슈팅의 관련 이슈는 이 이슈를 가리킨다.

- Epic: {{E1}}
- 선행: {{B03}}
- 설명 포인트: **테스트 계정 동시 대여 경쟁 (핵심)**

## 유저 스토리

- `US-WS-1` 방문자로서, 다른 방문자와 겹쳐도 내 계정이 온전히 내 것이길 원한다.
- `US-WS-7` 운영자로서, 한 네트워크가 계정을 독식하지 않길 원한다.

## 인수조건

- [ ] `AC-WS-05` 같은 빈 계정에 동시에 들어온 대여 요청 중 **정확히 한 건만 성공**하고 나머지는 "이미 대여 중"으로 거부된다. 성공한 비밀번호만 유효하다. **동시 요청 자동 테스트 필수** (스레드 N개 동시 요청 → 성공 1, 거부 N-1, 대여 레코드 1)
- [ ] `AC-WS-06` 같은 IP에서 동시에 대여 중인 테스트 계정은 1개다. 살아 있는 대여가 있으면 새 대여는 "이미 이 네트워크에서 대여 중"으로 거부된다. 같은 IP의 동시 요청도 하나만 통과한다. IP 식별은 인프라 결정(Caddy가 `X-Forwarded-For` 재작성, Spring `forward-headers-strategy=native`, HANDOFF 1장)을 따르되, 그 전에는 직접 연결 IP 기준으로 구현해도 AC는 성립한다. 대여 요청은 브라우저가 `/api`를 직접 호출한다 ({{C0}})

## 구현 시 결정할 것 (ADR 소재)

- 한 명만 성공시키는 방식: DB 유니크 제약·조건부 UPDATE·행 잠금(`SELECT ... FOR UPDATE`)·낙관적 락 중 무엇으로 보장하는가, 왜
- IP 동시 대여 판정을 같은 트랜잭션에서 어떻게 원자적으로 하는가 (IP 단위 유니크 제약 vs 조회 후 삽입의 경쟁)
- 동시성 테스트를 어떻게 재현 가능하게 만드는가 (실패한 시도 포함 → 트러블슈팅 소재)
