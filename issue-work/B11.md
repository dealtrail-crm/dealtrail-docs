## 배경

모든 CRM 데이터는 정확히 하나의 작업 공간에 속하고, 다른 계정의 세션으로는 "존재하지 않음"과 같은 결과를 받아야 한다. 모든 엔티티 CRUD 이슈의 선행이며, 이 Epic의 설명 포인트 "작업 공간 격리"의 **핵심 이슈**다. 교차 검증 테스트는 {{B12}}.

- Epic: {{E1}}
- 선행: {{B01}}
- 설명 포인트: **작업 공간 격리 (핵심)**

## 유저 스토리

- `US-WS-3` 방문자로서, 내가 만든 데이터가 다른 방문자에게 보이지 않았으면 한다.

## 인수조건

- [ ] `AC-COMMON-01` 모든 CRM 데이터(Lead, Account, Contact, Opportunity, Activity, 단계 이력)는 정확히 하나의 작업 공간에 속하고, 작업 공간 밖에서 조회·수정되지 않는다
- [ ] `AC-COMMON-02` 계정 A의 세션으로 계정 B의 작업 공간 데이터를 조회·수정·삭제하면 "존재하지 않음"과 같은 결과를 받는다 ("권한 없음"으로 존재를 노출하지 않는다)
- [ ] `AC-WS-27` 작업 공간 식별자와 계정 식별자는 추측 불가능하다 (순차 번호 금지). 엔티티 식별자 형식은 {{C0}}

## 구현 시 결정할 것 (ADR 소재)

- 세션 → 작업 공간 결정 위치: 필터/인터셉터에서 컨텍스트로 넣는가, 서비스 계층에서 매번 받는가. 누락을 컴파일·테스트 시점에 잡을 수 있는 구조인가
- "존재하지 않음" 응답 일원화: 조회 쿼리에 작업 공간 조건을 항상 포함시키는 방법 (리포지토리 공통화 등)
- 식별자 생성 방식: UUID v4/v7, ULID 등과 인덱스 영향
